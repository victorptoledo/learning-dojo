# Compilers and Interpreters: Lexing, Parsing, ASTs and Bytecode

Every language you use is implemented by a program that reads text and either translates it
(a **compiler**) or runs it (an **interpreter**). Most real implementations do both: `javac`
compiles Java to bytecode that the JVM interprets and then compiles again to machine code; CPython
compiles your `.py` to bytecode and interprets it; V8 parses JavaScript, interprets bytecode and
JIT-compiles hot functions. The pipeline is the same everywhere, and its first half (lexing and
parsing) is something you will write yourself many times: for config formats, query languages,
templating, DSLs.

## The pipeline

```text
source text
   │  lexer (scanner)
tokens
   │  parser
abstract syntax tree (AST)
   │  semantic analysis: names, scopes, types
annotated AST / symbol tables
   │  lowering
intermediate representation (bytecode, SSA, …)
   │  optimisation
   │  code generation
machine code   ── or ──   an interpreter / VM runs the IR directly
```

The **front end** (lexer, parser, semantic analysis) depends on the language; the **back end**
(optimisation, code generation) on the target machine. LLVM's success comes from that split: many
languages (Rust, Swift, Clang's C and C++) share one back end.

## Lexing

The **lexer** turns characters into **tokens**, the words of the language, and drops whitespace
and comments:

```text
total = price * (1 + rate)  →  IDENT(total) EQUALS IDENT(price) STAR LPAREN NUMBER(1) PLUS IDENT(rate) RPAREN EOF
```

Each token type is described by a **regular expression** (`[A-Za-z_][A-Za-z0-9_]*` for
identifiers, `[0-9]+` for integers), and a lexer is in effect a finite automaton: the topic of the
next phase. Rules: take the **longest match** (`>=` is one token, not two), then prefer keywords
over identifiers, and record each token's **position** for error messages.

## Grammars

The structure of a language is written as a **context-free grammar**, usually in (E)BNF. Each rule
says how a construct is made of smaller ones:

```text
expr   := term   (("+" | "-") term)*
term   := factor (("*" | "/") factor)*
factor := ("-" factor) | power
power  := atom ("^" factor)?
atom   := NUMBER | IDENT | "(" expr ")"
```

The grammar **encodes precedence** by layering: `*` lives one level below `+`, so it binds
tighter. It encodes **associativity** by the shape of the recursion: the loop in `expr` makes
`a - b - c` mean `(a - b) - c` (left associative), while `power` calling `factor` on its right
makes `2 ^ 3 ^ 2` mean `2 ^ (3 ^ 2)` (right associative).

An **ambiguous** grammar allows two trees for one input (the classic dangling `else`); language
designers remove ambiguity with rules like "an `else` belongs to the nearest `if`".

## Parsing

A **recursive-descent parser** has one function per grammar rule. Each looks at the current
token, consumes what it expects and calls the functions of the rules it contains:

```python
def term(self):
    node = self.factor()
    while self.peek() in ("*", "/"):
        op = self.next()
        node = BinOp(op, node, self.factor())
    return node
```

It is easy to write, gives good error messages ("expected `)` at column 14"), and is what most
production compilers use by hand: GCC, Clang, `javac`, Go, Rust, V8, Roslyn (C#). Variants and
alternatives:

- **Pratt parsing** (precedence climbing) handles many operator levels with a table of binding
  powers instead of one function per level.
- **LL(k)** parsers decide with k tokens of lookahead; recursive descent is LL. They cannot use
  left-recursive rules (`expr := expr "+" term` loops forever), which is why the rules above use
  loops.
- **LR parsers** (LALR, generated by yacc, Bison) read bottom-up and accept more grammars; parser
  generators such as ANTLR (LL(*)) produce the code from the grammar.
- **Parser combinators** build parsers from small functions in functional style.

## Abstract syntax trees

The parser produces an **AST**: a tree of the program's meaning without punctuation. `(1 + 2) * x`
becomes:

```text
    *
   / \
  +   x
 / \
1   2
```

Parentheses are gone: the shape of the tree says it all. Every later phase walks this tree:
formatters (gofmt, Prettier), linters (ESLint, Ruff), refactoring tools, and the compiler itself.

## Semantic analysis

The parser checks the **syntax**; it cannot know that `x` is undefined or that `"a" * true` is a
type error. Semantic analysis walks the AST with a **symbol table**, a stack of **scopes** mapping
names to declarations, to resolve every name, check types, and compute things such as which
variables a closure captures. Errors found here are the "compile errors" of statically typed
languages.

## Running the program

- A **tree-walking interpreter** evaluates the AST recursively: `eval(BinOp(+, l, r)) = eval(l) +
  eval(r)`. Simple, but slow: pointer chasing and a dispatch per node.
- A **bytecode compiler** flattens the tree into a linear sequence of instructions for a virtual
  machine. A **stack machine** (JVM, CPython, .NET's CIL, WebAssembly) keeps operands on a stack:
  emit the code of the children first, then the operator (a **post-order** traversal).

```text
(1 + 2) * x   →   PUSH 1, PUSH 2, ADD, LOAD x, MUL
```

  A **register VM** (Lua, Dalvik) names its operands instead and needs fewer instructions.
  Bytecode is compact, cache friendly and can be saved (`.class`, `.pyc`).
- A **compiler to machine code** lowers to an IR such as **SSA** (every variable assigned once),
  **optimises** (constant folding, dead code elimination, inlining, loop optimisations, register
  allocation) and emits instructions for the target ISA.
- A **JIT** (just-in-time) compiler, in the JVM's HotSpot, V8, .NET's RyuJIT and PyPy, starts by
  interpreting, **profiles** which code is hot and which types actually occur, then compiles those
  parts to machine code with **speculative** optimisations ("this `+` always sees ints"), and
  **deoptimises** back to the interpreter when an assumption breaks. That is why such programs
  have a **warm-up** period.

## Summary

- Compilers and interpreters share a front end: lexer → tokens → parser → AST → semantic analysis.
- Grammars encode precedence by layering and associativity by the shape of the recursion.
- Recursive descent, one function per rule, is the standard hand-written parser.
- Programs run as a tree walk, as bytecode on a VM (post-order code for a stack machine), or as
  machine code, possibly produced at run time by a JIT from profile information.
