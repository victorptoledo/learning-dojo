# Documenting Architecture

Architecture lives in people's heads until it is written down, and the usual written form, a
box-and-line diagram nobody can read without its author, explains little. Good documentation is
small, aimed at an audience, and kept next to the code so it stays true.

## The C4 model

Simon Brown's **C4 model** describes software at four levels of zoom, like a map:

1. **System context**: the system as **one box**, the **people** who use it and the **other
   systems** it talks to. For everybody, including non-technical people. It answers "what is this
   and what is around it?"
2. **Container**: the separately runnable or deployable parts inside the system: web
   applications, mobile apps, APIs, workers, databases, file stores, queues. (Not Docker
   containers, although they often map to them.) For developers and operations. It shows the
   major technology choices and how the parts communicate.
3. **Component**: the major building blocks **inside one container** (for example the modules of
   a modular monolith) and their responsibilities. For the developers of that container.
4. **Code**: classes and functions. Usually generated by an IDE when needed, rarely drawn by hand.

Most teams need levels 1 and 2 always and level 3 for the containers that are complex enough.

### Notation rules that make diagrams readable

C4 does not prescribe shapes or colours; it prescribes **clarity**:

- every element has a **name**, a **type** (person, software system, container, component), a
  **technology** where relevant and a short **description** of its responsibility;
- every relationship is a one-way arrow with a **description** ("reads and writes loans",
  "sends reminder emails using") and, from the container level down, a **protocol**
  ("HTTPS/JSON", "SQL/TCP", "SMTP");
- every diagram has a **title** and a **key** (legend);
- **one level per diagram**: no classes on a container diagram, no servers on a component diagram.

### Supporting views

- **System landscape**: all the systems of an organisation, for enterprise-level views.
- **Dynamic** diagrams: how elements collaborate for one use case, numbered steps (a sequence
  diagram works too).
- **Deployment** diagrams: how containers map to infrastructure (nodes, regions, clusters). This
  is where Kubernetes, load balancers and availability zones appear, not in the container diagram.

## arc42: the rest of the documentation

Diagrams do not say everything. **arc42** (Gernot Starke and Peter Hruschka) is a template of
twelve sections that tells you what else to write, and you fill only the useful ones:

1. introduction and goals (the top quality goals and stakeholders);
2. constraints;
3. context and scope (C4 level 1);
4. solution strategy (the few fundamental decisions);
5. building block view (C4 levels 2 and 3);
6. runtime view (dynamic diagrams);
7. deployment view;
8. crosscutting concepts (security, error handling, logging, persistence patterns);
9. architecture decisions (your ADRs);
10. quality requirements (the quality attribute scenarios of the first lesson);
11. risks and technical debt;
12. glossary (the ubiquitous language).

C4 and arc42 fit together: C4 gives the diagrams for sections 3, 5, 6 and 7.

## Diagrams as code, docs next to code

A diagram drawn in a drawing tool is out of date the week after. Keep diagrams as **text** in the
repository:

- **Structurizr DSL**: one model of people, systems, containers and relationships, from which all
  the views are generated, so an element renamed once is renamed in every diagram;
- **PlantUML** with the C4-PlantUML library, or **Mermaid** (which renders in GitHub and GitLab
  Markdown and has C4 diagram support);
- Markdown or AsciiDoc for arc42 sections and ADRs, built into a site with the rest of the docs.

Then documentation changes in the same pull request as the code it describes and is reviewed with
it. Some teams go further and generate the component level from the code, or check that the
documented dependencies match the real ones with the same graph the fitness functions use.

### Writing for an audience

Before documenting, ask who will read it and what decision they need to make. An onboarding
developer needs context, containers, the main concepts and the ADRs; an operations team needs the
deployment view and the runbooks; a business stakeholder needs the context diagram and the
quality goals. A short document that the reader actually uses beats a complete one nobody opens.
