Write `catalog.sql`: the products, and the discounts marketing invents for them.

**Types**

- A **domain** `sku` over `text`: three uppercase letters, a dash and four digits, such as
  `KTL-0042`. `SELECT 'ktl-0042'::sku` must already fail, with no table involved.
- An **enum** `product_status` with `draft`, `active` and `retired`, in that order (so
  `'draft' < 'active'` and an `ORDER BY status` follows the life of a product).
- An **enum** `currency` with `EUR`, `USD` and `BRL`, in that order. The next stage uses it.

**The table `products`**

| Column | Rule |
|---|---|
| `id` | `bigint` generated by the database, primary key |
| `sku` | of type `sku`, required and unique |
| `name` | `text`, required and not blank: `''` and `'   '` are refused |
| `status` | `product_status`, required, `draft` by default |
| `tags` | `text[]`, required, `'{}'` by default; see below |

The tags of a product:

- at most **5** tags;
- each tag is made of lowercase letters, digits and dashes (`outdoor`, `size-42`), so never
  `''` and never `NULL`;
- no tag twice in the same product.

`INSERT INTO products (sku, name) VALUES ('KTL-0042', 'Kettle')` must work, and every insert
that breaks a rule above must fail with `23514` (or `23505` for a repeated SKU, `22P02` for a
status the enum does not have).

> [!TIP]
> A `CHECK` cannot hold a subquery, and "no element repeats" or "every element matches" needs
> one: look inside the array with `unnest`. A `CHECK` can, however, call a function. An
> `IMMUTABLE` SQL function that takes the array and returns a boolean is allowed there (and
> it must really be immutable: same array in, same answer out). A domain over `text[]` can
> carry the same check, and reads well in the table.

Marketing wants new kinds of discounts every month. Instead of a column per idea, each
discount keeps its rule in a `jsonb` document, and the table still refuses a rule it does not
understand.

**The table `discounts`**

| Column | Rule |
|---|---|
| `id` | `bigint` generated by the database, primary key |
| `product_id` | required, references `products` |
| `rule` | `jsonb`, required, one of the shapes below |
| `kind` | the rule's `"kind"` as `text`, a **stored generated column** (nobody writes it) |

The two shapes a rule may have, and nothing else:

```json
{"kind": "percent", "value": 10}
{"kind": "bulk", "min_qty": 3, "value": 15}
```

- `value` is a JSON **number**, a whole one, from 1 to 90 (a percentage off);
- `min_qty` is a whole JSON number, at least 2;
- no other keys, no missing keys: `{"kind": "percent", "value": 10, "note": "x"}` is refused,
  and so are `{"kind": "percent", "value": "10"}` (a string), `{"kind": "percent",
  "value": 12.5}`, `{"kind": "bogo"}` and `[]`. Every refusal is a `CHECK` (`23514`).

> [!TIP]
> For the rules: inside a `CHECK`, `jsonb_typeof(rule -> 'value') = 'number'` tells a number
> from a string, `rule ?& array['kind', 'value']` checks that keys exist, and
> `rule - array['kind', 'value'] = '{}'` that there is nothing else. A jsonpath predicate can say a lot in one expression:
> `rule @@ '$.value.type() == "number" && $.value >= 1'`. Beware of casting before you know
> the type: `(rule ->> 'value')::int` on `"abc"` raises `22P02`, not `23514`, and the order in
> which a `CHECK` evaluates its `AND`s is not guaranteed; a `CASE` is.
