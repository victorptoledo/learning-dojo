Write `queue.sql`.

**The table `jobs`**

| Column | Rule |
|---|---|
| `id` | `bigint` generated by the database, primary key |
| `queue` | `text`, required: `'mail'`, `'images'`... |
| `payload` | `jsonb`, required, `'{}'` by default |
| `priority` | `integer`, required, `0` by default; a higher number runs first |
| `run_at` | `timestamptz`, required, `now()` by default: not before this moment |
| `status` | an enum `job_status` of `pending`, `running`, `done`, `dead`, in that order; `pending` by default |
| `attempts` | `integer`, required, `0` by default: how many times it was claimed |
| `locked_by` | `text`: the worker running it |
| `locked_until` | `timestamptz`: the end of that worker's lease |

**The functions**

- `enqueue(p_queue text, p_payload jsonb, p_priority integer DEFAULT 0, p_run_at timestamptz
  DEFAULT now()) RETURNS bigint` adds a pending job and returns its id.
- `claim(p_queue text, p_worker text) RETURNS bigint` takes the next job of that queue and
  returns its id, or `NULL` when there is none. The next job is the **pending** one whose
  `run_at` has come (`<= now()`), with the highest `priority`, then the earliest `run_at`,
  then the lowest `id`. Claiming it sets `status = 'running'`, `locked_by = p_worker`,
  `locked_until = now() + 30 seconds` and adds 1 to `attempts`.
- `complete(p_job bigint, p_worker text) RETURNS boolean` marks the job `done` and returns
  `true`, but only when it is `running` and `locked_by` that worker; otherwise it changes
  nothing and returns `false`.

**The races**

- Worker A claims inside a transaction that stays open; worker B claims from the same queue.
  B **does not wait**: it gets the next job. If A commits, a third claim gets the job after
  those two; if A rolls back, A's job is the next one again.
- A queue with one job: A claims it and stays open; B gets `NULL` at once.

**Fast with a long history.** Done jobs are kept for a while, so the table grows. With 200,000
done jobs and a handful pending, a claim must touch at most **60 buffers** (the tests run
`EXPLAIN (ANALYZE, BUFFERS) SELECT claim(...)`, which counts what your function reads).

> [!TIP]
> `SELECT ... FOR UPDATE` locks the row a worker picks, but a second worker that picks the
> same row waits for the first transaction to end: ten workers, one at a time. `FOR UPDATE
> SKIP LOCKED` makes the second one skip rows that are locked and take the next. Pick and
> update in one statement: `UPDATE jobs SET ... WHERE id = (SELECT id FROM jobs WHERE ...
> ORDER BY ... LIMIT 1 FOR UPDATE SKIP LOCKED) RETURNING id`. Then look at which index lets
> that `ORDER BY ... LIMIT 1` stop after a few rows when most of the table is `done`.
