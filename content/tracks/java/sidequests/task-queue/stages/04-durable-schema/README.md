Move the queue's state into PostgreSQL. Write two files at the top of the project; they are
checked in the `dojo-sql` image (PostgreSQL 17), while the Java tests keep running.

**`schema.sql`** creates the table `tasks`:

| Column | Type and rule |
|---|---|
| `id` | `bigint`, generated by the database, primary key |
| `type` | text, required, not empty |
| `payload` | text, required, default `''` |
| `status` | text, required, default `'ready'`, one of `ready`, `leased`, `done`, `dead` |
| `attempts` | integer, required, default 0, never negative |
| `available_at` | `timestamptz`, required, default `now()` |
| `lease_until` | `timestamptz`, set **exactly** when the status is `leased` |
| `idempotency_key` | text, optional, unique |
| `last_error` | text, optional |

Let the database enforce every rule in the table (`CHECK`, `UNIQUE`, `NOT NULL`): a bug in
one worker must not be able to write a bad row.

**`claim.sql`** is one statement that leases the next task, like `poll`:

- the candidates are the `ready` tasks with `available_at <= now()` and the `leased` tasks
  whose `lease_until` has passed;
- it takes the one with the oldest `available_at` (then the smallest `id`);
- it sets `status = 'leased'`, adds 1 to `attempts` and sets `lease_until` 30 seconds from
  `now()`;
- it returns `id, type, payload, attempts` of that task, or no row when nothing is ready.

Many workers run `claim.sql` at the same time, so two of them must never get the same row:
look up `FOR UPDATE SKIP LOCKED` in a subquery.
