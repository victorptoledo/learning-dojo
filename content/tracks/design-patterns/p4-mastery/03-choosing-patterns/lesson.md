# Choosing, Combining and Removing Patterns

You now know the patterns. The skill that remains is judgement: **which** one, **when**, and
**when to take it out again**.

## Start from the forces

Do not ask "which pattern can I use here?". Ask what the problem is pulling at:

| If the force is ... | Consider |
| --- | --- |
| an algorithm varies and variants keep arriving | strategy (lambda or class), registry |
| a closed set of variants, many operations over them | sealed records + switch (visitor style) |
| a closed set of states with transitions | state as sealed records |
| an object needs extra behaviour in some combinations | decorator |
| access needs control (transactions, security, laziness) | proxy (usually the framework's) |
| a foreign interface or model | adapter, anti-corruption layer |
| a complicated subsystem most callers use simply | facade |
| many optional construction parts | builder, or a record with defaults |
| families of matching objects | abstract factory, or DI configuration |
| others must react to something | observer, domain events |
| requests must be queued, logged or undone | command |
| a request passes through configurable steps | chain of responsibility, pipeline |
| business rules combine and must also become queries | specification |
| persistence and transactions must not leak into rules | repository, unit of work, ports and adapters |
| creation and wiring hard to test | dependency injection, composition root |

And if none of these forces is present, the answer is **no pattern**: a function, an `if`, a
record.

## Compare candidates by cost

Patterns often compete. Weigh them on what will change:

- **Strategy classes vs a switch over sealed types**: new variants cheap vs new operations cheap
  (the expression problem).
- **Decorator vs proxy generated by the framework**: explicit and testable vs less code and
  some magic (self-invocation).
- **Observer vs direct calls**: decoupling and extension vs explicit control flow and easy
  debugging.
- **Repository interface vs using Spring Data directly**: domain isolation and fakes vs less
  code and more framework surface.
- **Builder vs constructor**: readable optional parts vs one more class to maintain.

## Patterns travel together

| Combination | Where you saw it |
| --- | --- |
| strategy + factory/registry | shipping rules, Spring `Map<String, Bean>` |
| adapter + decorators | payment gateway, HTTP clients with interceptors |
| composite + command | macros |
| composite + interpreter + sealed types | specifications |
| builder + immutable record | quote requests, HTTP requests |
| observer + command | event-sourced or undoable systems |
| ports and adapters + repository + unit of work + DI | the hexagonal transfer |
| facade + adapters | an anti-corruption layer over a large legacy system |

## What Java and Spring already do for you

Do not hand-write what the platform provides:

- Lambdas and functional interfaces: strategy, command, template callbacks.
- Records: value objects, immutable prototypes, parameter objects.
- Sealed types and pattern matching: visitor, state, composite, interpreter.
- Enums: singletons and closed strategy sets.
- `Iterable`, streams: iterator, pipelines.
- Spring: DI and factories (container), proxies (`@Transactional`, `@Cacheable`), observer
  (application events), template methods (`JdbcTemplate`, `TransactionTemplate`), repository
  (Spring Data), chain of responsibility (filters, interceptors), strategy registries (beans by
  type).

## Removing a pattern

Patterns are not forever. Remove or inline one when:

- the variation it allowed never happened (one strategy for three years);
- the language now does it (a visitor over a sealed hierarchy, an iterator class over a
  stream);
- it hides a simple thing behind layers no one understands (`AbstractHandlerFactoryProvider`);
- the forces changed (the legacy system behind the ACL was retired).

Use the same discipline as adding one: tests first, small steps (Inline Class, Collapse
Hierarchy, Inline Function).

## Talking about patterns

In design reviews and interviews, patterns are vocabulary, not trophies. A strong answer:

1. states the **problem and forces** ("payment providers change, and checkout must not");
2. names the **pattern** and sketches it in a sentence ("an adapter per provider behind our
   own `PaymentGateway` port, with retry as a decorator");
3. gives the **cost** and an **alternative** ("an extra interface and mapping; we could call
   the SDK directly, but every test would need it");
4. points to **real use** ("this is how Spring's `@Transactional` proxy works", "`java.io`
   does the same with streams").
