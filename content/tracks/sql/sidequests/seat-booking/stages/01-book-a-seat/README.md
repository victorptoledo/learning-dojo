Write `booking.sql`:

**The table `bookings`**

| Column | Rule |
|---|---|
| `id` | `bigint` generated by the database, primary key |
| `show_id`, `seat` | required; together they reference `seats` |
| `customer_id` | required, references `customers` |
| `booked_at` | `timestamptz`, required, default `now()` |
| `cancelled_at` | `timestamptz`, `NULL` while the booking is active |

A cancelled booking stays in the table as history. A seat has **at most one active
booking**, and the table itself must refuse a second one (an `INSERT` of two active bookings
of a seat fails with a unique violation), whatever code writes to it.

**The functions**

- `book_seat(p_show integer, p_seat text, p_customer integer) RETURNS bigint` books the seat
  and returns the new booking's id, or returns `NULL` when the seat already has an active
  booking. A seat or customer that does not exist is an error (a foreign key violation).
- `cancel_booking(p_booking bigint) RETURNS boolean` cancels an active booking (sets
  `cancelled_at`) and returns `true`; it returns `false` for a booking already cancelled or
  an id that does not exist.

**The races**

- Two sessions book the same seat. The first one's transaction is still open: the second
  **waits** for it. If the first commits, the second returns `NULL`; if it rolls back, the
  second gets the seat. Never two active bookings, never an error.
- Two sessions book two different seats: neither waits.

> [!TIP]
> "Check that the seat is free, then insert" has a gap between the check and the insert,
> and under `READ COMMITTED` two sessions both see a free seat. A unique index has no gap: a
> second insert of the same key waits for the first transaction to finish. Which unique index
> fits "one **active** booking per seat"? And `INSERT ... ON CONFLICT ... DO NOTHING
> RETURNING id` turns the conflict into "no row".
