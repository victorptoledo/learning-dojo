When a show sells out, people join a waiting list; when a ticket comes back, a box office
offers it to the next person. Both box offices work through the same list at the same time.
Write `waitlist.sql`:

| Column of `waitlist` | Rule |
|---|---|
| `id` | `bigint` generated by the database, primary key |
| `show_id` | required, references `shows` |
| `customer_id` | required, references `customers` |
| `joined_at` | `timestamptz`, required, default `clock_timestamp()` (the moment of the insert, not of the transaction's start) |
| `offered_at` | `timestamptz`, `NULL` while the customer is still waiting |

A customer waits **at most once per show**, and the table refuses a second waiting entry.

- `join_waitlist(p_show integer, p_customer integer) RETURNS bigint` puts the customer on the
  list and returns the entry's id; when they are already waiting for that show, it returns
  that entry's id and adds nothing. After an offer, the customer may join again.
- `offer_next(p_show integer) RETURNS integer` takes the person who has waited longest
  (`joined_at`, then `id`), marks the entry as offered (`offered_at = now()`) and returns
  the `customer_id`; `NULL` when nobody waits.

**The races** (Ana, Bia and Caio wait for show 1, in that order):

- Box office A calls `offer_next(1)`, gets Ana and stays open. Box office B calls
  `offer_next(1)` at the same time: it does **not wait**, and gets Bia. After A commits, the
  next offer is Caio; if A rolls back instead, Ana goes back to the list and is offered
  next.
- Two sessions put Dani on the list at once: the second waits for the first, and both
  return the same entry id.

> [!TIP]
> `FOR UPDATE` makes the second box office wait for the row the first one locked, and then
> skip it because it is no longer waiting: one box office at a time. `FOR UPDATE SKIP LOCKED`
> passes over locked rows instead, which is how job queues hand out work. In `join_waitlist`,
> remember what `READ COMMITTED` lets a **new** statement see.
