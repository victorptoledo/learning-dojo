# Checkpoint 2: The Ticketing Schema

The dojo sells seats for its events. Today everything lives in one spreadsheet:

```text
venue     | capacity | event       | starts_at        | ends_at          | customer_email  | customer | seat | price
Main Hall | 3        | Kata Night  | 2026-12-01 19:00 | 2026-12-01 22:00 | ada@example.com | Ada      | A1   | 15.00
Main Hall | 3        | Kata Night  | 2026-12-01 19:00 | 2026-12-01 22:00 | grace@...       | Grace    | A2   | 15.00
Main Hall | 3        | Belt Exam   | 2026-12-05 10:00 | 2026-12-05 13:00 | ada@example.com | Ada      | A1   | 0.00
```

Normalise it into four tables, in `schema.sql`, with **these** names and columns (the tests
insert rows into them; ids are given by the inserts, so use `integer PRIMARY KEY` or
`GENERATED BY DEFAULT AS IDENTITY`, not `GENERATED ALWAYS`):

```text
venues    (id, name, capacity)
events    (id, venue_id, title, starts_at, ends_at)
customers (id, email, name)
tickets   (id, event_id, customer_id, seat, price)
```

Pick the types yourself (money is exact; points in time have a zone) and enforce these rules
with constraints, so that the database rejects any write that breaks one:

1. Every column is required (no NULLs).
2. A venue's name is unique and its capacity is greater than 0.
3. An event takes place in an existing venue and ends **after** it starts.
4. A customer's email is unique.
5. A ticket is for an existing event and an existing customer; its price is 0 or more.
6. A seat is sold at most once per event (the same seat at another event is fine).
7. Deleting an event deletes its tickets; a customer who holds tickets cannot be deleted.

Then write `availability.sql`, one query over your tables:

| Columns | Rows and order |
| --- | --- |
| title, venue name, tickets sold, seats left (capacity − sold), rank in venue | every event, also those with no tickets (0 sold); the rank orders the events of each venue by tickets sold, most first, ties share a rank with no gap (1, 2, 2, 3); order by venue name, rank, title |

There is no fixture: try it in `docker run -it --rm --network none -v "${PWD}:/work" dojo-sql play`
with `\i schema.sql`, then insert a few rows of the spreadsheet above. Each test runs your
`schema.sql` on an empty database, inserts valid rows, and checks that a bad write fails with
the right kind of error (for example SQLSTATE `23505` for a duplicate).

There are 18 tests: 1 in `tests/visible.sql` and 17 hidden ones.
